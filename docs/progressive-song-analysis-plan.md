# 歌曲分析的分段渐进处理计划

状态：规划，尚未实施。基于已推送的 `3c7bbfa1`。当前功能未发布，直接替换数据结构和处理链，不保留旧格式读取、迁移或两套播放实现。

## 目标与交互

点击后立即进入现有分轨界面，原曲继续播放。先计算当前播放位置附近的六轨；当前位置及前方缓冲准备好后，在同一音频时间轴上切入分轨。和弦消费已经就绪的伴奏片段，边处理边显示，不等整首六轨结束。

- 已就绪范围可以直接使用；首次仍有首段准备时间，不能承诺零计算延迟。
- 用户在两分钟处点击，优先处理两分钟附近，不从零点顺序排到那里。
- 拖动进度只改变任务优先级，已经有效的片段继续复用。
- 尚未切入分轨时保持原曲播放；切入前必须留足前方缓冲。
- 分轨已经生效后，如果拖入未就绪范围或缓冲耗尽，进入现有缓冲状态。**不自动恢复原曲**，避免重新放出用户已经静音的人声或乐器。关闭分析开关可显式回到原曲。
- 暂停、切歌、关闭分析开关沿用现有语义：界面开关不等于取消后台任务；明确的任务取消才停止计算。
- 歌词位置、底部播放控制、左侧分轨布局保持现有设计；进度列表仍然只显示歌名和状态图标，不增加项目管理页面。

首批交付六轨和和弦。主唱／和声、双歌手仍由用户明确触发；人声旋律／曲谱在核心链路稳定后接入同一调度器。

## 已确认的限制

1. `src/main/audio/musicStudyPlatform.ts` 先完整捕获网络音源，`worker.py` 再完整解码和读取 PCM。
2. `separation.py` 的 Demucs 已使用内部切块和 25% 重叠，但函数等整首结果合并后才返回；模型每次任务重新创建。
3. 当前阶段队列按整首推进。六轨可先于和弦启用，但一首歌内部没有可消费的就绪时间段。
4. `StudyMixInput.h` 要求完整 WAV、确定的总帧数和足够的文件长度，不能把增长中的 WAV 当作流直接播放。
5. 当前和弦路径为 SheetSage2/MERT2。模型输入窗口固定为 300 秒，短输入也会补到这个长度；当前 `paper` 设置为重叠 100 秒、lookahead 为 0。窗口转录具有双向音频上下文，**不是原生因果流式模型**。
6. 当前人声转写按最长约 45 秒的歌词组对齐，并从混音提取节拍。它适合逐句渐进输出，不能直接改成逐采样输出。

因此不能把现有函数套进小片段循环就宣称完成流式处理，也不能假定输入缩短十倍，和弦推理就加速十倍。

## 一条统一处理链

`音源解析 → 连续 PCM 解码／分段存储 → 六轨片段 → 和弦／可选人声分析 → 原生播放、歌词显示、CLI 与导出`

全曲处理完成只是所有必要时间段都已就绪。完整导出也从同一批片段生成，不另建一条整首离线分析链。只保存本功能必要的分析产物，不恢复之前移除的集中音乐资料库。

### 1. 输入和时间轴

新增由 Core 管理的分析音源会话。复用现有提供方解析、权限和源资源租约，分析链由连续解码器产出固定网格的 PCM 块。

- 统一使用 44.1 kHz 的整数帧范围 `[startFrame, endFrame)`；内部不靠累加浮点秒数对齐。
- 一个源版本绑定实际音频质量、编码延迟处理及 CUE 范围。旋转的 CDN URL 不作为歌曲或缓存身份。
- 分别记录已下载、已解码和可随机读取的范围。网易云边下载边解码，不再以全曲下载完成作为启动条件。
- 不假定所有 CDN 都支持 Range。只有确认支持字节范围及正确定位时，才承诺直接读取跳转位置；顺序输入需要暴露其实际可用范围。
- 总帧数未知时保持未知，元数据时长仅作提示；到达真正 EOF 后才能宣告整首完成。完整内容哈希尚未得到时，使用源会话身份和块内容哈希，不能伪造完整文件指纹。
- 原曲与分轨的交接明确处理编码器首尾填充、重采样、起始偏移及 CUE pregap，避免分段后歌词与音频逐渐漂移。

### 2. 常驻模型与调度

将逐次启动的分析进程改成应用拥有的常驻运行时，按需加载和复用模型。校验、加载和预热在后台执行；不把每首歌都变成一次 Python/CUDA 冷启动。

优先级按依赖和播放截止时间确定：

1. 当前请求位置所需的解码、六轨和上下文。
2. 即将播放的六轨缓冲。
3. 当前可用范围的和弦。
4. 用户明确请求的人声子轨和逐句曲谱。
5. 其他歌曲及远离播放位置的补全。

GPU 任务设置显存预算和并发上限，初始采用受控串行执行，不让多个重模型同时争抢 GPU。显存允许时保持模型常驻，否则按依赖和优先级管理驻留。已经进入 GPU 的运算不强行宣称可以即时抢占；调度器在安全边界重排任务。

片段网格固定锚定源帧零点，与点击位置无关。随机偏移、归一化和融合规则固定并可复现，避免同一段因为处理顺序或 Seek 不同产生不同结果。模型版本、窗口策略与归一化策略纳入缓存键。

### 3. 分段产物与协议

Core 是任务、可用范围和缓存清单的唯一管理者。SQLite 保存清单及事务状态；音频和较大的结果写入不可变文件，不在每次进度更新时重写整首结果 JSON。

协议由“整首 ready”改为明确的范围：

```ts
type FrameRange = { startFrame: number; endFrame: number }
type AnalysisAvailability = {
  sourceDecoded: FrameRange[]
  sixReady: FrameRange[]
  chordsStable: FrameRange[]
  chordsProvisional: FrameRange[]
  leadBackingReady: FrameRange[]
  twoSingersReady: FrameRange[]
  melodyReady: FrameRange[]
}
```

这是拟议的数据形状，不代表已经增加这些接口。各功能范围独立，不能拿六轨进度代替和弦进度。

- 六轨作为一个原子组提交：同一源范围的六个音轨全部对齐、文件写完并验证后，才发布 `sixReady`。
- 重叠融合区完全确定后才能提交；尚待相邻窗口参与融合的尾部不能提前交给播放器。
- 文件先写临时路径，关闭后原子提交，再更新清单。崩溃恢复只承认已提交块，丢弃未完成临时产物。
- 源版本决定缓存归属；请求 generation 决定当前界面是否接收通知。Seek 不删除有效缓存，切歌后旧任务也不能覆盖新歌界面。
- 下载、推理和原生读取使用资源租约，删除任务须先完成取消和释放，避免读写中的文件被移除。

### 4. 原生分轨播放

用新的分段输入替换 `TEMIX1`／完整 WAV 的播放入口。完整结果仍通过这一入口读取已提交块，不保留第二套旧播放器。

- 原生解码工作线程异步准备块并混音，实时音频回调只消费已准备的 PCM；回调内不读文件、不等待模型、不分配大块内存。
- 缺块、取消、真正 EOF、损坏分别表示。缺块不能返回 EOF，也不能补静音后继续走播放时钟。
- 同一帧位置同时读取所有被选择音轨；增益、静音、独听继续走现有即时控制接口。
- 切入前依据处理速度和就绪范围计算前方缓冲。原曲切换到六轨使用短交叉淡化，保持位置、暂停状态和歌词时钟。
- 用户改变音轨选择后，不能通过自动回原曲悄悄改变试听含义。

### 5. 和弦逐段发布

优先复用当前高精度模型，不先引入另一个低精度模型维持表面上的“秒出结果”。必须先验证现有固定窗口模型的真实延迟和短上下文质量。

- 和弦使用已经提交的伴奏范围，不等待整首六轨完成。
- 分离音频块大小与和弦上下文大小独立；和弦不必跟着每个几秒音频块重新跑一次。
- 可从解码器输出完整、符合语法的和弦事件后提前发布，不把 token 数量当成可用结果。
- 同一编码窗口内部可复用解码状态；音频上下文改变后，不能错误复用旧窗口的编码特征或 decoder KV。
- 为窗口定义输入上下文、接受范围和待确认尾部。缺少分析结果的范围保持未知，不能填 `N` 冒充真实无和弦。
- 相邻窗口先统一绝对时间，再融合重叠区；人工校正永远优先。
- 当前播放视图固定已经播放过的时间锚点和标签，未播放的待确认尾部才允许调整。分析修订和显示绑定分开管理，避免和弦在歌词上左右跳动。
- 调性估计与和弦时间轴分开。罗马级数变化不能重新排列歌词或谱面；主调修订需要明确的版本策略。

### 6. 人声拆分与曲谱

主唱／和声模型已有分窗循环，可以在六轨人声块就绪后接入。双歌手扩散模型还需要逐窗音色状态与 A/B 锚定，不能承诺跟六轨一样快，也不能为了追赶播放而交换歌手身份。

人声旋律按完整歌词句或短歌词组处理，取得足够节拍／声学上下文后提交。已分离人声、识别音符、谱面排版分别缓存；沿用现在的弱起／不完整尾小节，避免重新引入首尾补位 `0`。

所有这些任务都不能阻塞基础六轨的播放缓冲。

## 分阶段实施

| 阶段 | 交付 | 进入下一阶段的条件 |
|---|---|---|
| M0：能力与性能实验 | 真实模型窗口、重叠、归一化、冷／热启动、显存和质量数据；确定首段与缓冲参数 | 明确当前模型能否满足持续处理速度；和弦固定窗口的限制有实测结论 |
| M1：范围数据链 | 连续解码、固定 PCM 网格、原子块存储、常驻运行时、Core 范围查询与通知；CLI 可观测 | 局部读取、取消、进程重启和范围一致性通过，尚不自动接管播放 |
| M2：六轨渐进播放 | 当前位置优先、原生块读取、交接、Seek 和缓冲策略 | 六轨可以在整首未完成时稳定试听，音轨控制和原曲切换无回归 |
| M3：高精度和弦渐进显示 | 伴奏范围驱动的窗口推理、事件发布、稳定／待确认范围和修订策略 | 首段／接缝质量通过，与歌词和播放时钟一致，已播放内容不跳动 |
| M4：可选人声功能 | 主唱／和声、双歌手、逐句旋律与谱面接入同一调度器 | 不影响基础六轨缓冲，歌手顺序和词谱映射稳定 |
| M5：完整交付 | CLI 批量与局部导出、网络音源、多曲风和资源压力验证 | 所有输出均从同一分段数据生成，旧链路已删除 |

M0 应测试 Demucs 的真实训练／推理窗口限制，不把之前讨论的“8–12 秒”当成已经支持的配置。和弦对 15／30／60／120 秒可用上下文和完整基准做对照，并独立记录固定 300 秒补齐带来的计算成本。缩短编码窗口或改变上下文策略，都必须单独验证，不能继续把结果标为原始 `paper` 协议。

如果当前模型无法同时达到延迟和质量要求，先提交实验结论及可选方案，再决定是否更换模型；不能静默降低模型或准确率。

## 验收与测量

以下是 RTX 5080 上的**初始设计预算，不是已经测出的性能承诺**，M0 后应调整并记录：

- 本地音频暖启动首段六轨 P95 目标不超过 3 秒，冷启动目标不超过 8 秒。
- 首段高精度和弦暖启动目标不超过 10 秒，独立统计等待伴奏的时间。
- 稳态六轨＋和弦处理的实时时间比目标不超过 0.5，预留下载、GPU 抖动和交接余量；不把双歌手扩散计算包含在这个承诺内。
- 分开统计网络取流、首段下载、解码、校验、模型加载、推理、存储、IPC 和真正可听交接，报告 P50/P95，不用单一“总耗时”掩盖等待。

必须验证的行为：

1. 从零点、中途点击、连续 Seek、暂停时启用、切歌、关闭／重新开启和多任务抢占。
2. 缺块、断网、损坏、进程退出、取消期间写文件、磁盘压力和 GPU 显存不足。
3. 音轨之间无帧偏移、重复或遗漏；导出拼接与原生播放读取同一批块。内存随活动窗口有界，不随整首长度线性增长。
4. 多曲风和公开有真值样本，与固定版本的当前完整分析基准比较。首段、接缝和无真值试听分别报告，不能用整首平均掩盖首段质量问题。
5. 和弦详细性质的初始质量预算为相对当前基准下降不超过 1 个百分点，最终门槛由 M0 确定；无真值歌曲只评价流程与听感，不声称准确率。
6. 确认 CPU／低显存环境的实际能力；不能追赶播放时采用明确的准备／缓冲行为，不伪称实时。

## CLI、导出与旧内容清理

范围状态、优先位置、取消和等待通过 Core 协议提供，CLI 命令仍由协议生成。批量任务复用同一调度器；部分分析结果不标记成整首完成。局部导出必须验证请求范围已经就绪，完整导出等待所需全曲范围，不能导出缺块的静音文件。

实施时删除完整 WAV 试听入口、`TEMIX1` 解析、只发布整首结果的 worker 接口和整首阶段串行门槛。新的数据格式直接替换现有未发布 schema，开发分析缓存可清理，不写旧版本迁移代码。保留原歌曲、账号数据和独立安装的模型文件。
