# 歌曲分析预加载与缓存方案

状态：已实施并完成 Windows 本机验证。2026-10-31。此方案替代已取消的实时分段分析计划。验收记录见 [song-analysis-preloading-validation.md](song-analysis-preloading-validation.md)。

采用整曲分析、常驻运行时、下一首预分析，以及有容量上限的音频缓存。保留现有模型和完整音频上下文；不实施渐进 PCM、局部就绪范围播放或短上下文和弦协议。

## 1. 已确定的产品行为

1. 点击“分析歌曲”，当前歌曲优先执行六轨和和弦。六轨完成后按当前开关状态启用分轨，和弦完成后按当前显示意图打开。底部播放控制、歌词布局和桌面歌词保持现有交互。
2. 六轨音频允许淘汰，设容量上限，按最近实际使用时间删除最久未使用的音频组。和弦、原始音符、歌词对应关系及最终谱面独立长期保存。
3. 后台复用 Python 运行时和已加载模型，减少每次任务重新导入依赖、校验及加载模型的成本。六轨“暖态计算快”不等于所有点击都瞬时完成。
4. 只预分析实际队列的下一首，不遍历整个歌单、喜欢列表或本地目录，不恢复集中音乐资料库。
5. 预分析只准备数据。是否使用分轨、显示和弦或曲谱，由用户当前的功能开关决定；后台任务完成不能替用户打开已关闭的功能。
6. 主唱／和声与双歌手拆分继续明确点击才执行，不自动预分析。

## 2. 已有测量与解释边界

本机为 RTX 5080。以下用于规划，不是新架构的验收结果。

| 项目 | 已有记录 | 说明 |
|---|---:|---|
| 60 秒音频的现有整曲六轨纯计算 | 0.917 秒 | 单样本，不含运行时启动、下载、完整读写与可听交接 |
| Python 依赖导入 | 16.19 秒 | 一次冷启动记录，不保证每次都相同 |
| 六轨模型加载 | 0.427 秒 | 与 Python 导入分开计时 |
| 《青花瓷》约 4 分 29 秒的和弦阶段 | 15.342 秒 | 阶段计时，不等于端到端等待 |
| 同曲人声旋律／歌词对齐／排谱阶段 | 约 79–87 秒 | 历史合并记录，不能归为纯旋律模型推理耗时 |
| 同曲和弦缓存文件 | 8,787 字节 | 当前 JSON 文件大小 |
| 同曲原始音符缓存文件 | 74,188 字节 | 包含时间与歌词映射等数据 |
| 同曲最终谱面缓存文件 | 294,882 字节 | 68 行 SVG 及元数据，平均每行约 4 KB |
| 同曲当前全部非音频生成目录 | 约 2.95 MB | 含排版中间文件、重复 SVG 和结果副本 |

因此这首歌的和弦、音符及最终谱面核心数据合计约 0.38 MB，压缩率尚未实测。不能将 0.38 MB 当成任意歌曲的固定上限。

三分钟六轨 float32 双声道 44.1 kHz PCM 约 381 MB，另有原曲 PCM、输入副本和可选子轨。缓存统计必须覆盖整个分析音频工作集。

模型安装文件为一次性占用：六轨约 55 MB，和弦及编码器约 2.76 GB，人声旋律相关模型包约 445 MB；不包含 Python 环境及排谱工具，不随每首歌重复保存。磁盘模型文件与模型驻留的 RAM／显存分别统计。

## 3. 常驻运行时与模型复用

### 生命周期

- 应用拥有运行时；Core 拥有分析任务、优先级、结果有效性及缓存策略。平台层负责进程、文件、设备及授权音源 IO，不另建一套独立任务队列。
- 保留现有两套依赖环境的隔离：主分析运行时负责六轨、和弦及可选拆分；人声旋律运行时负责 TiFA／GAME 等组件。共同接受 Core 调度，不因每首歌曲创建完整分析环境。
- 配置环境可用后在后台预热六轨与和弦，应用界面、普通播放及已缓存识别结果读取不等待预热。
- 人声旋律组件在首次需要时启动并预热，后续复用；不在用户从未使用旋律功能时自动运行识别。
- 正常换歌不卸载六轨与和弦模型。内存压力时先释放可选组件；确需卸载时记录冷／暖状态，不能继续按暖启动耗时展示或验收。
- 预热和每次分析结束释放未使用的 CUDA 缓存。Core 分析队列、音源准备或运行时请求活跃时保留 GPU 模型；队列空闲满 30 秒后，在同一串行执行器上把和弦模型移到内存，六轨留在 GPU。下次真正识别和弦前恢复 GPU，复用同一模型对象和原精度。读取已有和弦／谱面不恢复模型。详见 [song-analysis-gpu-residency.md](song-analysis-gpu-residency.md)。
- 首次载入完整校验模型；已验证版本在同一运行时内复用，文件或环境变化重新验证。避免每首歌重复读取数 GB 模型进行相同校验。
- 各能力按需导入依赖。六轨就绪不应被未请求的双歌手组件或已退役的产品模型依赖阻塞。
- 切换环境、应用退出或 Core 重启时，先停止接收任务，再取消并等待当前任务和子进程退出，最后释放资源；新一代运行时不能接收旧任务的结果。

### 推理协议

- 请求与事件携带 requestId、jobId、generation、sourceVersion 和明确阶段。过期回调不能修改当前歌曲或任务状态。
- 一个阶段可独立复用其依赖和结果。查询缓存结果不启动模型；音频缺失也不要求先生成六轨才能显示现成的和弦、音符或谱面。
- 保持现有六轨的整曲归一化、随机平移及 Demucs 内部分窗行为，不采用首版实验的外层重复切窗。
- 和弦保持当前 SheetSage2/MERT2 整曲 `paper` 协议。300 秒仍为模型内部窗口参数，不采用实验性的独立窗口接受策略，不改变模型准确率以追求启动速度。
- GPU 推理初始按串行调度，模型可同时驻留；不把模型驻留等同于并行运行所有分析。

## 4. 小型识别结果与音频彻底解耦

### 独立产物

| 产物 | 长期保留内容 | 无需依赖仍在磁盘上的六轨 |
|---|---|---|
| 和弦 | 时间、名称、识别来源、人工校正、算法及输入签名 | 是 |
| 原始旋律 | 音高、原始起止时间、节拍与时值、调式、歌词原文及对应关系 | 是 |
| 最终谱面 | 逐行 SVG、音符索引、排版版本及原始音符签名 | 是 |
| 六轨与可选子轨 | 完整、对齐的音频文件组及清单 | 否；可按需重新生成 |

当前 `studyCache.ts` 在原曲或六轨缺失时直接让全部阶段失效，必须替换这种校验方式。

- 有效性依据稳定的音源版本、模型版本、算法参数和对应输入签名，不依据父音频文件现在是否仍存在。
- 源版本包含实际内容身份、音质、解码语义及 CUE／pregap 范围；网易云旋转 CDN URL 不作缓存身份。不能把同一 songId 的不同录音或音质错误混用。
- 保留生成时的音源／父产物指纹。清理六轨只改变音频可用性，不抹掉已确认的小结果及其来源。
- 歌词变化只使相应的对齐与谱面失效；排版版本变化只重排；切换和弦名称／罗马级数或现有显示调式不重新识别。
- 已有人工校正独立保存，并在同一音源版本的模型重算后继续优先应用。
- 单阶段失败保留其他有效阶段，不能因曲谱生成失败而删除和弦或六轨。

### 唯一持久化来源

Core 管理的 SQLite 保存任务、产物来源、有效性及缓存清单。建议将体积较小的和弦、音符、最终谱面作为压缩产物存储，每种产物只有一个持久化副本；项目摘要保存引用及状态，不再嵌入整份 SVG 和音符。

运行时写入不可变音频文件，由 Core 验证并提交清单。播放器和导出从同一份完整音频读取。保留现有完整音频播放路径，不增加分段播放器。

`study.state` 只返回轻量摘要；当前歌曲及主动请求的 CLI 查询再读取对应结果。歌词时钟更新不能反复传输整首 SVG，也不能为软件内和桌面歌词各存一份结果。

## 5. 谱面存储与生成

1. 原始音符与歌词映射为可再生源数据，识别与排版分别缓存。
2. 最终谱面只保留一份，按整首打包压缩，内含各行索引。读取后提供当前所需行给软件内歌词、桌面歌词及 CLI。
3. MusicXML、LilyPond 源码、未裁剪／重复 SVG 和临时 MIDI 放在任务临时目录。最终谱面提交成功或任务失败后清理临时目录。
4. MIDI、MusicXML、PDF 等用户导出按请求生成到授权导出目录；用户导出文件不计入可自动删除的内部缓存。
5. 谱面缓存命中时直接读取，不因六轨淘汰重新识别或排版。谱面丢失而原始音符有效时，仅重排。
6. 每批最多 16 行调用同一 LilyPond 原生进程；保留现成排版器，验证弱起、尾小节、连音、字体、原词和时间映射，不手写替代排谱引擎。取消时终止并等待本次拥有的进程。

## 6. 音频缓存上限与 LRU

### 初始策略

- 初始默认上限 2 GiB，设置中显示为 2 GB，并允许修改。大致容纳四首三分钟歌曲的完整分析音频，实际随音源和子轨变化。
- 计入分析拥有的编码音源副本、原曲 PCM、六轨、人声子轨、混音描述文件及临时音频；模型安装文件、小型结果和用户导出分别统计。
- 原有本地歌曲不属于缓存，不移动或删除。借用现有播放音源缓存时复用既有资源租约，不再多复制一份同内容源文件。
- “最老”定义为最久未实际使用的音频组，不是最早分析的歌曲。普通进度轮询、读取和弦或显示曲谱不刷新六轨的 LRU。
- 六轨作为一个原子组提交和淘汰，不留五条轨道冒充六轨可用；可选人声子轨是独立音频组。

### 容量与并发

- 开始下载、解码或推理前预留工作空间；计算已提交字节、临时文件及其他任务预留，避免完成后才发现超限。
- 正在播放、推理输入、导出、等待原生切换确认的音频均持有租约。缓存只能淘汰未被占用的音频组。
- 当前播放和已确定下一首分别持有必要租约，防止刚预分析完就被后台清理；队列变化后释放过期的预取租约。
- 没有可淘汰空间时，后台任务等待或跳过；前台明确返回缓存容量不足，保留已有小型结果。不悄悄超出设置上限，也不删除仍在使用的文件。
- 单首工作集大于上限时同样适用该规则，用户可调整缓存容量。运行中调低上限先停止新增后台预留，待受保护工作集释放后继续回收，并显示实际占用。
- 删除先在清单中标记，再移入缓存拥有的回收区域，确认实际删除后减少占用统计。Windows 文件占用导致删除失败时保留真实计数，不谎报清理成功。
- 重启时只协调清单及本功能拥有的临时／回收目录，恢复容量账目，清理未提交文件；不扫描音乐目录。

### 淘汰后的使用

- 和弦、简谱、五线谱、桌面歌词及 CLI 数据读取照常可用。
- 再开启分轨时，只补齐缺失音频；已有效的和弦与旋律不重算。
- 只导出和弦／音符／谱面时不要求音频；导出分轨音频时先生成缺失轨道并持有租约。
- 网络音源暂不可取时，现有小型结果仍可读取；音频恢复任务单独报告失败。

## 7. 下一首预分析与任务优先级

### 触发与范围

- “预分析下一首”默认开启，但仅在当前播放会话实际启用了分析能力时工作；普通听歌且未启用分析时不自动运行歌曲分析。
- 只读取 Core 当前歌曲和已确定的下一首。使用实际队列顺序、occurrenceId 与队列版本，不在渲染层猜测，也不消耗随机数来预测下一首。
- 当前会话使用六轨／和弦时，下一首优先准备六轨与和弦；旋律仅在当前已启用人声曲谱时加入预分析。多人声拆分始终按需执行。
- 某项已有有效结果就跳过该项及不再需要的音频依赖。例如已有和弦、只为下一首显示和弦时，无需恢复六轨；若下一首需要分轨播放则仍须恢复音频。
- 单曲循环复用当前结果。下一首未确定的推荐模式先不猜测；播放顺序明确后再准备。
- 队列变化后撤销旧预取需求，停止尚未执行的任务并在安全点取消无其他需求的后台任务。已经完成的小型结果可保留。

### 优先级

1. 当前歌曲由用户触发的六轨、和弦、旋律或人声拆分。
2. CLI 明确请求的前台任务；与第 1 类按提交顺序及明确的当前播放需求协调。
3. 已确定下一首的预分析。
4. CLI 批量分析等其他后台任务。

同一音源、阶段及参数的任务合并。后台任务成为当前歌曲时直接提升优先级；取消一个预取需求不能取消另一个用户或 CLI 正在等待的共享任务。

“前台优先”不等于可以强行中断 GPU 内核。运行时在 Demucs 内部窗口、和弦生成步骤及旋律组边界响应取消；仅对外提交完整阶段结果。无显式安全取消点时记录实际最长等待，不宣称立即抢占。取消推测任务应尽量保留已加载模型。

关闭功能后停止为其新建预取需求；已经由用户明确启动的当前任务沿用现有取消语义。后台完成事件不能重新打开已关闭的歌曲视图。

## 8. 现有界面与 CLI

- 保留歌曲内分析图标、和弦／级数、简谱／五线谱、人声轨下拉菜单及现有过渡动画。
- 设置增加“预分析下一首”、音频缓存容量、已用容量及“清理音频缓存”。不增加独立资料库或项目管理页面，不添加解释性长文案。
- 顶部分析列表仍为歌名加进行中／已完成图标，同一歌曲不因预取、手动请求和反复切歌产生重复条目。
- Core 分别返回音频可用、和弦有效、原始音符有效和谱面有效状态，避免一个总 ready 状态掩盖差异。已淘汰音频的已识别歌曲再次生成六轨时可显示进行中，原有和弦和曲谱照常显示。
- 拟增加 `study.runtime`、`study.cache` 查询，以及 `study.setCachePolicy`、`study.clearAudioCache` 命令；具体输入校验、权限与返回结构由 Core 协议定义，再生成 CLI。
- 现有 CLI 分析、等待、取局部和弦／音符、导出谱面与批量任务走相同缓存和调度器。等待以实际请求的能力为准，不因音频被淘汰误判小结果失效，也不能把音频缺失的导出标为成功。

## 9. 实施顺序

| 阶段 | 工作 | 验收重点 |
|---|---|---|
| P0：基线与计时 | 分开记录环境校验、依赖导入、模型加载、下载、解码、推理、歌词对齐、排谱、写盘、IPC 与可听交接 | 冷／暖、命中／未命中及重排分别计时，避免复用旧的合并计时得出错误结论 |
| P1：常驻模型 | 应用拥有运行时、按需导入、模型复用、生命周期及请求代际 | 连续分析多首只加载一次对应模型；正常播放与缓存查询不等待启动 |
| P2：独立产物 | 替换音频存在性驱动的失效逻辑；小型结果单份压缩保存；排谱临时文件清理 | 删除所有分析音频后仍可显示／导出和弦和曲谱，重建六轨不重跑小结果 |
| P3：有上限音频缓存 | 原子组、空间预留、LRU、租约、实际字节计数与崩溃恢复 | 播放／分析／导出期间不误删，缓存不因临时文件及失败删除静默超限 |
| P4：下一首预分析 | 对接真实队列、功能意图、去重、取消与优先级 | 正序／随机／循环／插队／连续切歌正确，无旧任务接管当前歌曲 |
| P5：界面、CLI 与性能 | 简洁设置、统一查询和导出；多曲风、重启、失败及资源压力验证 | 缓存命中不启动模型；CLI 与软件内／桌面显示一致；六轨和分析精度不退化 |

P1、P2、P3 完成后再开启自动预分析，避免在没有容量和依赖管理时生成大量音频。

## 10. 必测场景与性能口径

功能测试覆盖：

- 六轨被淘汰后和弦与谱面仍有效；只有谱面被删除时只重排；只有歌词变化时只重做对应对齐／谱面。
- 当前分轨播放、音量／静音／独听、导出、下一首预取同时发生时的租约与清理。
- 同曲重复队列项、音质切换、CUE 范围、原文件移动或修改、网易云 URL 轮转及试听片段。
- 队列变更、快速切歌、关闭分析开关、取消共享任务、进程退出、应用重启、环境变更、磁盘不足和 Windows 文件锁。
- 同一份小型结果供软件内歌词、桌面歌词与 CLI 使用；读取已有谱面不需要 Python 运行时处于可用状态。
- 现有原生播放器、弱起／尾小节、连音、音符原词映射、调式显示与罗马级数切换回归。

在 RTX 5080、音源已取得、无后台推理占用时，以三分钟样本的暖态六轨**端到端可用 P95 不超过 5 秒**作为初始优化目标，包含解码、推理、提交、IPC 和交接；尚未实测通过。网络等待和安全取消等待另报，不能从统计里隐藏。

和弦先以阶段暖态 P95 不超过 15 秒为初始目标，完整默认分析仍计入六轨依赖；旋律先完成逐阶段计时，再制定优化目标，不承诺模型预热能将当前约一分钟以上的词谱任务降到几秒。

缓存命中重点验收“无推理、无重新排版、无全音频哈希扫描”，并测量实际切换与渲染延迟。音频容量是字节预算；小型结果报告实际压缩前后体积，不强行把所有歌曲约束为 300 KB。

所有识别使用当前固定模型与完整上下文做同音频回归，不用降模型、短上下文或降低音频精度换取指标。
